# アーキテクチャ

## 基本方針

- 可能な限りC# に寄せる
  - 最新の.NETに追従する
- グラフィックスなどはC++を使うがC# にバインディングを露出させ、ライブラリとして利用する

## C# コードの実行基盤

- CoreCLR
  - JIT (RyuJIT) による .NET ランタイム
  - 公式には Windows, Linux, macOS に対応
  - 動的生成コードの実行が許可されていないプラットフォームでは技術的に動作させられない
- Mono
  - CoreCLR 以前から存在するオープンソースでクロスプラットフォームの .NET ランタイム
  - 移植性に優れる
  - 実装が古く CoreCLR のほうが高性能なので、今あえて選択されることは少ない
- NativeAOT
  - AOT (Ahead-of-time) コンパイルによる .NET 実行環境
  - RyuJIT によるコード生成を事前に行うようなアーキテクチャを取っている
  - iOS など JIT が禁止されているプラットフォームでも動作できる
  - 一部利用できる API に制限あり
- C++ へのトランスパイル
  - .NET 中間言語を C++ にトランスパイルする戦略
  - C++ コンパイラが提供されている環境であれば簡単に移植できる
  - Unity の AOT ソリューション IL2CPP
  - 一部利用できる API に制限あり

## GC

.NET はヒープ上に確保した参照型オブジェクトを自動的に破棄するガーベジコレクタ (GC) を利用する。いくつかの実装を比較する

- CoreCLR GC
  - CoreCLR 既定の GC 実装
  - どちらかというとサーバーアプリケーション向けに最適化されている
  - https://github.com/dotnet/runtime/blob/main/docs/design/coreclr/botr/garbage-collection.md
- Satori GC
  - リアルタイムアプリケーション向けに最適化された CoreCLR 用の実験的な GC
  - https://github.com/dotnet/runtime/discussions/115627
- Boehm GC
  - Mono が利用している GC
  - Unity が利用しているフォーク：https://github.com/Unity-Technologies/bdwgc

|      | CoreCLR GC        | Satori GC (CoreCLR, 実験的) | Boehm GC (Mono)|
|------|-------------------|--------------------------|------------------------|
| 正確性  | 精密 (precise)      | 精密                       | **保守的 (conservative)** | 保守的 |
| 移動/圧縮 | あり（コンパクション）       | あり（リージョン単位）              | **なし (non-moving)**    |
| 世代   | Gen0/1/2 + LOH/POH | Gen0（スレッドローカル）+ 上位世代     | なし（実質単一世代）             |
| 停止時間 | ms〜数百ms（Gen2次第）   | サブms級                    | ヒープ全体に比例               |
| 断片化  | 少ない               | 少ない                      | **多い**                 |


- **正確性**: GC がスタック上に存在するオブジェクト参照の位置を正確に把握しているかどうか。GC はこれらのルート参照を起点に、参照されているオブジェクト参照を辿っていく（マーク・アンド・スイープ方式）。GC がオブジェクト参照の位置を正確に把握していなくても、スタック上のあらゆるポインタがオブジェクト参照でありうるという仮定をもとに GC を実行することは可能で、こうした実装は「保守的」GC と呼ばれる。保守的 GC はアンマネージドコードからマネージドオブジェクトを単純なポインタで参照するだけで GC が追跡できるため、ネイティブ相互運用性に長けている。
- **移動/圧縮**：一度ヒープ上に確保されたオブジェクトが GC を通して移動するかどうか (moving GC, non-moving GC と呼ばれる)。GC による確保と解放にが繰り返されると次第にヒープは断片化し、新たなメモリ確保の効率低下や、ヒープ全体の肥大化を招く。こうした断片化を解消するためにオブジェクトを移動させることがある（コンパクション）。移動されるオブジェクトに対する参照（ポインタ）を追従させる必要がある点が高コスト。
- **世代別 GC**：オブジェクトを寿命の長短に応じて異なる管理を行う方式。確保されて間もないオブジェクトは頻繁に回収し、回収されなかったオブジェクトはより寿命の長い「世代」に移動させ、回収頻度を下げる。
- **停止時間**: GC の行う仕事の中の一部では、全てのマネージドスレッドを停止する必要がある (Stop-the-World 問題)。特にゲームではこの停止がフレーム時間の瞬間的な増大を招きスパイクとして現れ、ゲームプレイの快適性を損なう恐れがある。Unity の incremental GC は Boehm GC を拡張したもので、GC の仕事を複数のフレームに渡って実行されるように分割することで、スパイクの発生を抑えている。

## オーサリング

- ランタイムでも必要に応じてオーサリング機能を利用可能にしておく

## プロジェクト構成

### DivisionEngine

エンジンのコアライブラリ

### DivisionEngine.Player

### DivisionEngine.Editor

エディタ環境・オーサリング機能を提供するライブラリ

### DivisionEngine.Authoring

オーサリング機能を提供するライブラリ

### DivisionEngine.Generators

Source Generator と Analyzer を提供するコンパイラ拡張アセンブリ。エンジン・オーサリング・ユーザーコードの各プロジェクトから `OutputItemType="Analyzer"` で参照される。

コンパイラ（csc）にロードされるため、依存は `Microsoft.CodeAnalysis`（Compiler 層）のみに制限する。

### DivisionEngine.Generators.CodeFixes

Analyzer の診断に対する CodeFix を提供するアセンブリ（例: `DIVSER005` に対して現在の型名から計算した GUID の `[TypeId]` を自動挿入）。IDE から Analyzer 参照経由でロードされる。

Generators と分離しているのは意図的なもの。CodeFix は `Microsoft.CodeAnalysis.Workspaces` 層に依存するが、コマンドラインビルドのコンパイラ実行環境には Workspaces が存在しないため、コンパイラ拡張と同居させると CLI ビルドでのロードが保証されなくなる（`RS1038`）。CodeFix はコマンドラインビルドでは使われないので、Workspaces 依存をこちらに隔離している。ID 計算ロジック（`SerializedTypeGuid`）は Generators 側のソースをリンクして共有し、コンパイル時とランタイムの計算一致を保つ。
